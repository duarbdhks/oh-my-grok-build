# 전체 upstream 포크를 택하지 않은 이유

[English](upstream-evaluation.md)

이 문서는 [`NOTICE.md`](../NOTICE.md)에 적힌 업스트림 영감 프로젝트(`oh-my-claudecode`, MIT)를 포크하지 않기로 한 설계 근거입니다. 아래에서는 정식 이름을 다시 쓰지 않고 “원본”·“upstream”만 사용합니다.

## 최종 판단

좋은 아이디어이지만, **전체 포크가 아니라 Grok Build 네이티브 플러그인으로 재설계할 때만** 권장합니다.

## 선택지 비교

| 기준 | 전체 포크·이름 치환 | Grok 네이티브 플러그인 |
|---|---:|---:|
| 초기 구현 속도 | 4/5 | 4/5 |
| Grok 기능 적합성 | 2/5 | 5/5 |
| 유지보수성 | 1/5 | 4/5 |

| 총평 | 11/30 | 26/30 |

## 전체 포크가 불리한 이유

원본은 단순 프롬프트 모음이 아닙니다. 호스트 전용 플러그인 런타임, Node.js CLI, 에이전트 SDK 브리지, 상태 저장, 훅, 브리지, tmux 기반 외부 CLI 작업자, 설치·마이그레이션 로직을 함께 가집니다. 이를 Grok Build에 맞추려면 이름 치환이 아니라 런타임 경계를 다시 작성해야 합니다.

동시에 Grok Build는 이미 다음을 네이티브로 제공합니다.

- 플러그인과 마켓플레이스,
- 사용자·프로젝트 스킬과 에이전트,
- 병렬 서브에이전트와 capability mode,
- git worktree 격리,
- 저장 가능한 Rhai 워크플로,
- 장시간 자율 실행 `/goal`,
- 최종 독립 검증 `check-work`.

따라서 원본의 실행 엔진을 옮기면 두 개의 상태 머신, 두 개의 작업 관리 체계, 두 개의 병렬 실행 규칙이 충돌합니다.

## 가져올 가치가 있는 부분

- 계획과 실행의 명확한 경계,
- Planner → Architect → Critic의 순차 합의,
- 독립 작업을 파동으로 나누는 실행 규율,
- 구현자와 분리된 검증자,
- 최신 테스트 증거 없이는 완료를 주장하지 않는 규칙,
- 고위험 작업의 롤백·중단 조건.

## 가져오지 않은 부분

- 호스트 전용 모델 티어와 라우팅,
- tmux CLI 작업자,
- upstream 자체 상태 JSON과 세션 훅,
- 외부 에이전트 SDK 브리지,
- 신규 MCP 서버,
- Grok Build가 이미 가진 worktree, workflow, goal, memory 기능.

## 주요 위험

1. **Grok Build 확장 인터페이스 변화**: 2026년 7월 기준 기능 확장이 빠르므로 `plugin.json`, agent frontmatter, workflow 스키마를 릴리스마다 확인해야 합니다.
2. **프롬프트 기반 강제의 한계**: 훅 없는 콘텐츠형 플러그인이므로 계획·검증 경계는 권한 모드와 지침을 함께 사용해야 합니다.
3. **병렬 비용**: Grok 네이티브 워크플로 기본 예산은 큰 작업을 허용하므로 이 플러그인은 8개를 기본값으로 명시합니다.
4. **워크트리 병합 충돌**: 작업 소유권을 잘못 나누면 병렬화 이점이 사라집니다.

## 권고

v0.1은 현재 구조처럼 콘텐츠형 플러그인으로 출시하고, 실제 Grok 세션의 설치·계획·병렬 수정·검증 시나리오를 통과한 후에만 정적 Rhai 워크플로를 배포하는 것이 적절합니다.
